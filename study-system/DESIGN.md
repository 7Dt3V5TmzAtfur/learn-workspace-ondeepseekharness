# 学习资料 AI 辅助系统 · 架构设计

> 目标：上传任意格式文档 → 读前建构 → 读中加工 → 读后考核，全程遵循 `原则/` 目录中的学习规律。

## 0. 第一性原理

这条决定其他所有取舍，写在最前面因为后面每一节都是它的推论。

**错误的第一性原理**（本系统前三版实际在做的）：
> "要帮用户把这资料学完。"

推论出来必然是：覆盖率、高亮占比、每段都标、QA 至少 6 条。
为了把覆盖率从 1.6% 刷到 11%，会给每段机械找一句话，
产出「维度」「按需」「比单写」这种 4 字碎片 ——
界面更满、更难看、用户一个点都没记住。那是**负价值**。

**正确的第一性原理**（`原则/C1.03.b/反完成主义阅读.md`）：
> 帮用户从一份资料里拿到**能改变他行为的那几句话**。

三条推论，直接决定了三处设计：

| 推论 | 设计后果 |
|---|---|
| 进度不能是"完成了多少" | 主指标是「已经拿到 64 处能复述的要点、12 道自测」，不是「已标 182/182 段」 |
| 入口必须是"我想解决什么" | 读前六段式第②段先问"对我的帮助"，不是先给目录 |
| 摩擦必须极低 | 六段式默认只给 2796 字骨架（原 5845 字），细节折叠；单元目录默认收起 |

**不做什么**（和"做什么"同样重要）：
- 不设"每单元必须有 N 个知识点"这类配额 —— 一旦有配额，模型就会凑。
- 不把覆盖率做成阻断 —— 覆盖率只提示，永远不拦。
- 不做多层审计文书 —— 参考项目给它自己的产物配了 10 个审计账本，
  那是完成主义的另一种形式。用户原话："弄得太复杂就不想看书了。"

## 1b. 三层拆分

```
┌─────────────────────────────────────────────────────────────┐
│  界面层  Client 插件  @local/dsh-study-copilot (client.js)    │
│  ├ 侧栏面板 "学习工作台"（main 面板，key = study-copilot）    │
│  ├ 输入框停靠条：当前文档 · 阶段 · 下一步                      │
│  ├ 三色注意力阅读器（渲染宿主给好的 HTML）                     │
│  ├ 术语追问（选中文字 → 带 ¶N 上下文）                        │
│  ├ 知识图谱（iframe 嵌入 archify 生成的 HTML）                 │
│  └ 费曼考核 / 读前建构                                        │
├─────────────────────────────────────────────────────────────┤
│  能力层  Host 插件  @local/dsh-study-copilot (index.js)       │
│  ├ 多格式提取  extract.js（pdf/docx/pptx/xlsx/html/epub/…）   │
│  ├ 项目存储    store.js    <workspace>/.study/<docId>/        │
│  ├ 规则校验    rules.js    标签/三色预算/六段式/目标分级       │
│  ├ 内容渲染    markdown.js Markdown→HTML（短语级高亮）         │
│  ├ 图谱生成    archify-figures.js → archify CLI → HTML        │
│  ├ Agent 工具  study_ingest · study_read · study_save         │
│  │             study_term · study_status · study_drill        │
│  ├ HTTP API    /study-copilot/api/*（数据 + 图片资源）         │
│  └ 提示词段落  systemPrompt.section（声明工作流）              │
├─────────────────────────────────────────────────────────────┤
│  方法层  技能  .dsh/skills/study-*                            │
│  study-companion 总控 → preflight → annotate → map            │
│                     → recall → explain-term → feynman         │
└─────────────────────────────────────────────────────────────┘
```

**为什么这样切分**

- **插件 = 机制，技能 = 方法。** 提取格式、落盘、算覆盖率、渲染三色、算图坐标，这些是确定性计算，写成插件；"怎么拆解语义、怎么定重难点、怎么出思考题"是判断，写成技能让模型执行。两者不重叠。
- **同一个操作两个调用者。** 界面上的"导入文档""保存标注"和 Agent 的 `study_ingest`/`study_save` 调的是同一个 Host 服务方法（`StudyService.*`），没有两套逻辑。
- **界面不自己算，也不自己解析。** 宿主返回的 `/project` 里，每段都带渲染好的 `html`
  （高亮已经嵌在里面），图谱给出 `figures[]` 的 URL。界面只做三件事：插入 HTML、填 iframe 的 src、处理点击。
  这样"什么算粗体""标签怎么折行"只实现一次。**这条是踩过坑之后加的**：早期版本让客户端
  自己逐行输出 `<p>`，结果是粗体显示成字面星号、表格塌成一堆竖线、图片显示成链接源码。
- **技能可单独使用。** 不安装插件时，技能仍能靠纯文本工作（降级路径在技能里写明）。

### 2.0 入口与预览接口（v5 新增）

| 路由 | 用途 | 要点 |
|---|---|---|
| `POST /ingest-upload?name=<文件名>` | 浏览器上传文件 | 请求体是原始字节，不是 multipart，也不包 JSON。文件先落 `_inbox/<时间戳>-<名>` 再走同一条 `ingest`；落盘名带时间戳防覆盖，但**标题保持干净** |
| `GET /peek/:docId` | 30 秒预览 | 只读已有产物，零额外生成。返回字数、估算分钟、单元数、前两层目录、开头/结尾/最长一块各一句原话 |

`peek` 的三个约束（都是踩过的坑）：

1. 单元的 `id` 只指向标题那一段（`¶4` 的全文就是 `## 工具的分类`），正文在 `segmentIds` 里 —— 按 `id` 找句子永远找不到。
2. 没有 `units.json` 的小资料也要出目录：直接从段落里认 `#`~`###` 标题，否则 8 段带三个小标题的文章会显示"1 块、目录为空"。
3. 结尾抓手在有单元时按单元倒序找，没单元时按真实段落倒序扫；只用前者，小资料的结尾会等于开头。

### 2.1 单元骨架（v4 新增，把三处断裂接起来）

在此之前有三个同一病根的断裂，都是"182 段平铺、没有中间层"：

| 现象 | 修复前 |
|---|---|
| 知识点无法跳回原文 | 18 个知识点，0 个带 `segmentIds` |
| 图谱节点与段落脱钩 | 33 节点，0 个带 `segmentId` |
| 读前 parts 是模型编的切法 | 4 个 parts，0 个带 `segmentIds`；原文有 20 个真实小节 |

`units.json` 是中间层：**原文小节 → 段落 → 知识点** 靠它串成一条线。

切块规则（`tests/build-units.mjs`）：

1. 认两种小标题：Markdown `## 标题` **和** 加粗单独成段 `**小标题。**`。
   只认第一种会切出 45 段与 2 段并存的不均衡块。
2. 大标题下不足 300 字 → 合并紧跟的加粗小节（否则出现点进去什么都没有的条目）。
3. 合并后超过 2500 字 → 不合并，各小节独立成块。
4. 标题去掉末尾句号。
5. 生成时自校验五项：不重、不漏、无空块、有原文范围、大小不失衡（≤40 倍）。
   不过就拒绝写文件。

当前结果：25 块 / 182 段，中位 809 字，最大/最小 33.9 倍。

### 2.2 回指（每条知识点的来路）
`preflight.json` 的每条 `knowledgePoints[]` 带：

- `segmentIds` —— 原文段落号，界面渲染成「看原文 ¶N」，点了跳过去并闪一下
- `mappingSource` —— `manual` | `auto`，标明这条是怎么定位的

**找不到就不挂**，界面显示灰色「原文位置待定位」。
原则：挂错比不挂更糟 —— 用户点「三层防护」跳到讲 MCP 投毒的段落，
会以为自己记错了。所以自动匹配之上还有一张人工覆盖表。

关系图的节点遵循同一条规则，代价更明显：33 个节点原来 **0 个**挂 `segmentId`，
图上每个方块点下去都没有下文。补它的脚本 `tests/case-node-segid.mjs`
只用一种证据 —— **带 `quote` 的边的 `from` 端**，并且该段必须真的在讲它。
两级过滤都试出来是必须的：

| 试过的做法 | 结果 | 判断 |
|---|---|---|
| 节点标签里的关键词去原文搜，唯一命中就采用 | 「工具爆炸」命中 ¶182（思考题）、「代理工具」命中 ¶65（讲的是 Pi 的架构）、「信任边界」命中 ¶176（全章小结） | **放弃**。关键词只知道字出现在这里，不知道这里在讲它 |
| 边的两端都继承 | ACI 被指到 ¶2（电影开场），因为那条 quote 讲的是 `from` 不是 `to` | **放弃**。主语在前，这个顺序不能忽略 |
| 带 `quote` 的 `from` 端 + 该段主题校验 | chapter4 11/33，chapter1 19/33 | **采用** |

覆盖率就是 73% / 58% 这类数字，没有更高。**不为了数字好看去猜。**
证据不足的节点 `segmentId` 留空，界面在「知识点出处」里如实写
「另有 22 个知识点没有确切的原文落点」，而不是把它们列成可点。

### 2.2.1 标注是怎么来的（v5 新增）

`annotated` 阶段只看有没有标注条目。于是脚本批量回填出来的 182 条
也点亮了「读中完成」—— 而 chapter4 的 `annotations.json` 自己就写着
`backfillNote: "quote 由脚本从原文机械回填，建议让模型重新精标"`。
系统明知那是机械产物，却仍然对外说这一段读完了。

**为什么不改判定**：改 `annotated` 的定义会让已有项目从「已完成」掉回「没读」，
而「读过」本身无法被机器验证。用一个更严的判据替换一个宽松的判据，
只是把一种形式主义换成另一种。

**改法**：`service.provenanceOf()` 只看来源、不评判，`status` 与 `project`
都带上 `provenance`：

| kind | 什么时候 | reliable |
|---|---|---|
| `none` | 一条标注都没有 | false |
| `backfilled` | 有 `backfillNote`（脚本补齐的） | **false** |
| `mechanical` | 有 `mechanical-quote` 类 issue | false |
| `judged` | 有标注且无上述痕迹 | true |

界面在统计行旁边挂一个虚线小标签写「脚本回填（不是逐段判读）」，
鼠标悬停给出 `advice`。模型看到 `reliable: false` 就该提议重标，
而不是接着往后推进阶段。

**它出现在三处**（少一处就等于没说）：资料列表的段数旁边写「· 回填」；
输入框停靠条上挂「标注是脚本回填的」；`study_status` 返回完整 `provenance`，
系统提示里明确要求模型据此说话。

`progressOf` 里另存一个布尔 `backfilled`，因为列表页与停靠条都已经调过
`progressOf`，不该为同一个判断再把 `annotations.json` 读一遍。
**但它不参与 `stage` 的推导** —— 这是刻意的，理由见下面 2.3。

### 2.2.2 阶段判定为什么不收紧（v5 的取舍）

`annotated` 的判据是 `Boolean(annotation?.items?.length)`：只要有一条标注就算。
它宽，但**故意不收紧**。

试过三种改法，都否掉了：

| 改法 | 后果 |
|---|---|
| 要求 `provenance.reliable === true` | chapter4 从「已完成」掉回 `planned`，等于逼用户重标 182 段。正是《反完成主义阅读》要反对的 |
| 要求覆盖率 ≥ X% | 更糟：直接变成"把每段都标一遍"的配额 |
| 要求 ≥1 条 `core` | 实测三份资料结果完全一样，只是换个说法，没解决任何问题 |

根本理由：**`stage` 是导航，不是评分。** 导航只回答"下一步去哪"。
一旦它承担"你读了几成"，就必须先定义"读"——而"读"无法被机器验证，
任何替换判据都只是把一种形式主义换成另一种。

真正受害的是"以为自己读完了"的人，这个伤害靠 `provenance` 解决：
它不说"你没读"，只说"这批标注是谁标的"。让看到的人自己决定信几分。


### 2.3 阶段名与阶段状态：各只有一处真值

**阶段名**：`rules.js` 的 `STAGES`。
之前界面叫「读完自测 / 费曼考核」、服务端叫「读后自测 / 读后考核」、
技能文档叫「读后巩固 / 读后考核」——三套名字。
用户说"我要做费曼考核"，Agent 却在找 `study-recall`，就串线了。
现在界面页签、`next.message`、`/stages` 接口都取自同一张表，
`audit-docs.mjs` 还会校验 `SKILL.md` 的 description 以对应名字开头。

**阶段状态**：`store.js` 的 `stageFromProgress(progress)`。

`meta.json` 里曾经有个 `stage` 字段，没有任何代码维护它，
只是某个历史时刻写进去的死值。实际后果：
chapter4 的 `meta.stage` 是 `drilled`，但 `drills.jsonl` 是空的
（从没有过真实复述记录）—— 列表显示"已考核"，
下一句提示却让你"去做读后考核"，自相矛盾。

现在 `meta.stage` 一律被忽略，`list()`、`fullProject()`、
`nextStepOf()` 全部走 `stageFromProgress`。
七个阶段：`empty → ingested → planned → annotated → mapped → recalled → done`。

不变式（有测试守着）：**`nextStepOf(p).stage` 必须恒等于 `stageFromProgress(p)`**。

**读前六段式**（对应第 1–6 项要求）

1. `summary` — 300 字左右摘要
2. `goals` — ①这份资料对我（学习者）的帮助（第一、第二） ②总目标 ③子目标
3. `difficulty` — 每一部分的重点、难点
4. `assessment` — 每一部分的考核方式（了解/理解/掌握/熟练掌握 + 目的 + 达标要求）+ 知识点与内容、备注
5. `exercises` — 思考题与作业（费曼驱动）
6. `references` — 参考资料清单

界面上 ③④ 的细节默认折进 `<details>`：5845 字 → 默认可见 2796 字（-52%）。

## 3. 阅读中的三色注意力

七色语义（`多色编码阅读标记.md`）收敛为三档，避免"每句都标 = 没标"：

| 档位 | 颜色 | 语义来源标签 | 用途 | 预算 |
|---|---|---|---|---|
| 1 核心 | 橙 `--sc-core-line` `#f59e0b` | `#d` 定义 / `#s` 结论 | 必须能复述的骨架 | ≤ 全文 10% |
| 2 攻坚 | 品红 `--sc-hard-line` `#c026d3` | `#q` 疑问难点 / `#v` 验证 | 必须停下来想的地方 | ≤ 全文 8% |
| 3 参考 | 青 `--sc-ref-line` `#14b8a6` | `#e` 例子 / `#t` 迁移 / `#c` 备注 | 需要时回查 | 不限，但不参与精读 |

深浅两套主题各有一组 token（浅色深字 `--sc-*-fg` 配浅底 `--sc-*-bg`，深色反过来）。
底色只用于**短语**（`--sc-*-bg`）；段落本身不染色，只用 2px 左边线 `--sc-*-line` 表示档位。

**来源说明（必须诚实）**：

- **来自 `原则/` 的是**：七个渐构角色标签（`#d/#s/#q/#v/#e/#t/#c`）、
  预算上限 10–20%（`深度阅读的二八法则.md`）、"高亮必须落在原文短句上"。
- **我们自己定的、原则里没有的**：把七色**收敛成三档**、
  以及具体选**橙/品红/青**这套配色。原则只给了七类语义，
  没规定收敛成几档、也没规定颜色。
  这样做的理由：档位超过三档，用户在阅读中无法即时判断归属；
  颜色超过三种，视觉噪点会盖过语义本身。

插件在保存标注时校验：总高亮占比 ≤ 20%（二八法则），每段至多 1 个档位，
`#c` 标签必须带两字关键词，且 quote 不能是 ≤6 字的碎片
（`FRAGMENT_QUOTE_MAX_CHARS`，纯标题段豁免）。

## 4. 进度状态（五个阶段，七个状态）

五个**学习阶段**是动作：`preflight → annotate → map → recall → feynman`。
项目的**状态**由产物推导（`stageFromProgress`），共七个值，没有 `drilled`：

```
empty ──ingest──▶ ingested ──preflight──▶ planned ──annotate──▶ annotated
   ──map──▶ mapped ──qa──▶ recalled ──有效复述──▶ done
```

`done` 表示考核通过（`drills.jsonl` 里存在 `valid` 记录）。
图谱与自测都只依赖 `annotated`，可以任选顺序；`quiz.md` 在读前就生成，
所以"考核"阶段只由 `drills.jsonl` 的真实记录点亮。

每个阶段插件都返回"下一步该调什么"，技能里写明该阶段要交付什么、达标标准是什么。

### 4.1 主推荐与轻推荐（v5 新增）

`stage` 只说明"你现在在哪"，它**不阻塞任何操作**——五个工具随时可调，产物随时可写。
真正的问题从来不是"被锁住"，而是系统只告诉用户**一条**路，而且总是最重的那条。

实测证据：三份真实资料里，两份（217 段、182 段）走完了读前、标注、图谱，`drills` 仍是 0；
唯一一份产生过有效费曼复述的，是那篇只有 11 段的小资料。**流程越重，越没人走到底。**

所以 `recommendFrom(progress)` 同时给两个推荐：

| 字段 | 含义 | 出现条件 |
|---|---|---|
| `next` | 按顺序该走的那一步 | 总是有（`done` 阶段为 `null`） |
| `light` | 更轻的一步：合书把已经看懂的那一点讲一遍 | 已拿到成果（有 core 要点或 QA）、还没做过有效复述、且主推荐不是考核 |

`light` **只推荐、不上锁**。不做"解锁"机制：解锁要求先证明自己读过了，
而"读过"本身无法被系统验证，最后必然退化成完成主义。

`light` 在三个地方露出：`/projects` 每项的 `light`、`/project/:docId` 的 `light`、
`study_status` 的 `light`（模型据此可以主动说"不必读完也能先试"）；
界面在输入框停靠条上以「也可以」标签展示。

## 5. 界面设计

**入口**：左侧栏一个书本图标（`sidebar.panellist` id = `study-copilot`），点击进入主面板。
**导入**：主面板空状态就是一个方框，接住三种投喂方式 —— 拖文件进来、点选文件、粘路径。
三者最后收敛到同一条 `ingest` 逻辑（上传的先落到 `_inbox/` 再走路径导入），不会漂移。
失败必须说清是哪一种（无后缀 / 空文件 / 路径不存在 / 路径是文件夹），不能只说"失败"。
框下另有一行支线："手里还没有文件？说说你想解决什么"——只有问题的用户不该被赶走。
**预览**：导入后先给 30 秒预览（`GET /peek/:docId`），回答"要不要读"而不是"怎么读"：
分几块、多少字、约多分钟、开头/结尾/最长一块各一句原话。
点「开始读」直接看正文；「先看学习计划」才是次要出口——读前建构是承诺，不是门槛。
**主面板**：五个 Tab，名字与顺序全部取自 `GET /stages`（即 `rules.js` 的 `STAGES`）：
读前建构 / 读中加工 / 知识图谱 / 读后巩固 / 读后考核，默认停在「下一步该做的那一步」。
**输入框停靠条**：显示当前文档 + 阶段 + 主推荐，右侧可带一个「也可以」的轻推荐。

**精读页（Tab 1）的层次**，从上到下正好是用户心里的三个问题：

| 位置 | 内容 | 回答的问题 |
|---|---|---|
| 顶部单元目录（默认收起） | 「这份资料分 25 块 · 182 段」，每行一块带段数与要点数 | 这资料讲几件事？ |
| 要求条（默认收起，常驻一行） | 当前这一块的档位徽标 + 标题 + 「这一块要达到什么」 | 这里该读到什么程度？ |
| 图例行 | 三色语义 + 「分 25 块，25 块已看过」+ 标注来源标签 | 我在哪？ |
| 正文 | 短语级三色高亮；段落只用 2px 左边线标档位，不整行染色；段号与渐构角色（`#d`）退到左侧留白，悬停才显形；首行缩进 2em；核心档默认盖住待回想 | 这一段说什么？ |

单元目录刻意默认收起：想直接读的人不该被目录挡路。
图例里不放完成度百分比 —— 那会让人为了填满去标碎片。

**要求条**（v5 新增）解决的是读前页与正文之间的断裂：读前页写着这一部分要「掌握」、
要求能复述五类工具、难点是别把它当成 2×N 矩阵，一点进正文这些字全没了。
现在按 `preflight.parts[].segmentIds` 反查当前可见段落属于哪个 part，
滚动时自动切换。段落 → part 的映射靠两路：`segmentIds` 精确，
`unitIds` 展开成单元段号补全 —— 后者是必需的，chapter1 的 `part.segmentIds`
只覆盖 16% 段落，不展开 `unitIds` 就会大半时候不显示（展开后 71%）。

**读中追问的语音**（v5 新增）：语音识别依赖浏览器与厂商云服务，失败是常态。
原来的 `rec.onerror` 是个空函数 —— 麦克风点了亮一下又灭，用户不知道是没说、
没给权限，还是浏览器不行。现在按 `ev.error` 分类型给出下一步：
`not-allowed` → 去站点设置允许麦克风；`no-speech` → 再说一次；
`audio-capture` → 检查设备；`network` → 服务器没连上；`aborted` → 用户自己停的，不报错。
每条都附「手打一个词也一样能问」的兜底。缺少 `SpeechRecognition` 时
不留一个点了没反应的按钮，直接说明此浏览器不支持。


**读前页（Tab 2）**
- 六段式按 ①②③④⑤⑥ 分块，左侧竖排导航
- ③④ 的细节折进 `<details>`：5845 字 → 默认可见 2796 字
- 每个知识点右侧「看原文 ¶N」→ 切到精读页、滚到那一段、闪 1.6 秒
- 没有回指的知识点显示灰色「原文位置待定位」，不给假链接

**渲染职责划分**

| 内容 | 宿主产出 | 界面动作 |
|---|---|---|
| 段落正文 | `segments[].html` | 插入 HTML |
| 六段式 | `preflightHtml` | 插入 HTML + 事件委托接「看原文」 |
| 思考题 / 参考 | `quizHtml` / `refsHtml` | 插入 HTML |
| 图谱 | `figures[]`（archify HTML 的 URL） | `<iframe src>` |
| 图片 | `/asset/<docId>/<path>` 路由 | `<img src>` |

**术语追问（对应 3min.top 那种"指着词就问"）**
- 选中正文任意词 → 面板右下浮出气泡，显示选中的字 → 点「问这个词」
- 选区取值必须用 `getSelection().toString()`（写成 `String(selection)` 会拿到 `[object Selection]`）
- 语音提问走浏览器自带的 `SpeechRecognition` / `webkitSpeechRecognition`（Chrome / Edge 有，Firefox 没有）。
  它依赖厂商云服务，所以失败是常态：`onerror` 必须按 `ev.error` 分类型给出下一步动作，
  不能统一沉默。**这一条只验证到代码路径，没有用真麦克风跑过** —— 需要人在真实设备上确认。
- 回答必须结合**当前段落上下文**：提问时自动带上 `¶N` 段落原文

**知识图谱**
- 嵌的是 **archify 生成的 HTML**，不是 Mermaid 源码，也不是手绘 SVG
- `relations.json` 保存成功后宿主自动调 archify，产物 `graph-N.html` 落在 `.study/<docId>/`
- 超过 18 节点按根节点自动拆图：archify 的 `browser-check` 会按视口缩放判断字号可读性，
  33 节点铺 4348px 宽缩到 1440 后 12.5px 字变成 4px，会被判定不可读而拒绝出图
- 界面上方一排按钮切换子图，下方 `<details>` 列关系清单，附"新窗口打开"
- 出图失败不阻塞阶段推进（关系数据已存好），界面显示失败原因
- 图里的方块由 archify 自己渲染，界面插不进手，所以「回到原文」做在
  「知识点出处」清单里（只列挂了 `segmentId` 的，见 §2.2）

**怎么拆图**（v5 重写，旧实现有两个实测抓到的错）

拆不是审美选择：33 个节点铺出来必然超宽，archify 的 `browser-check`
按视口缩放判字号可读性，会被拒绝出图。

旧实现的两个错：

| 错 | 实例 |
|---|---|
| 同一节点出现在多张图 | chapter4 的「能力形态谱系」「默认取向」「披露策略」等 9 个节点出现在 2~3 张图里。用户会以为是两个不同概念——比少画一张严重得多 |
| 碎片图 | 分布 18/11/11/2/5/4，那张 2 节点的图是第 1 张被截断的残渣，它内部的关系在别处已经画过 |

现在的四步：

1. **按依赖边求连通分量**。依赖边（前置 / 整体-部分 / 包含 / 次序 / 因果）是骨架；
   对比、例证、类比、应用是旁证，不决定谁和谁同一张图。实测依赖边占 68%~73%，
   这个区分有数据支撑。
2. **分量超过上限才按拓扑层号切**，每块覆盖一段从基础到派生的连续层级。
3. **零边的组并回邻居最多的那张图**（不超上限的前提下）。
   孤立概念不为它们各开一张图。
4. **每个节点只归属一张图**。跨图关系记进 `crossRefs`，靠界面说明，不靠重复画节点。

**节点上限是量出来的，不是猜的**：从 18 逐档加到 26 拿去跑 archify，
四道门全过，`DEFAULT_MAX_NODES = 25`。取 25 是因为它刚好让两份资料的零边组都归零
（chapter4 → 22/6/5，chapter1 → 25/8），再往上加不减少组数，只让单张图更挤。
`service.js` 不再传自己的 `maxNodes`：写死一份在那里等于同一概念存两份，早晚漂移。

**重建图前必须清掉上一轮 archify 的证据文件**。不清会报
`viewer/evidence-path-conflict` / `ownership-receipt-schema-mismatch`，
整张图判失败——实测确认：目录里预置一个旧格式的同名 `graph-N.browser-check.json`，
`finalize` 立刻 `ok:false`。这个坑只在"出过图、后来升级过 archify"的机器上出现，
也就是所有真正用过的机器。删这些文件安全：它们是派生产物，每次 `finalize` 重新生成。

**三色高亮**
- 宿主端在段落 HTML 里把 `quote` 逐字命中处包成 `<strong class="sc-hl-{tier}">`
- 界面按 `data-id="¶N"` 切出每段 HTML，用 `dangerouslySetInnerHTML` 插入
- 段落本身**不染色**（`<section class="sc-seg">` 没有颜色 class）——整段变色等于没标

| 图谱质量 | 几何指标 + Pillow 预览图 | `tests/check-graph-quality.mjs` |

**两条教训**（都是踩过的）：

1. 只断言"接口 200"和"HTML 里出现 class 名"是不够的 ——
   这两个都通过时，界面仍然可能一个字都不显示。
   测试必须断言**输出的内容**（粗体是不是 `<strong>`、
   表格是不是 `<table>`、边有没有穿过节点）。
2. **全绿的测试也可能是错的。** 知识点回指 18/18 通过后，
   人工抽查发现 2 条挂到了不相干的段落上。自动校验只能保证
   "段号存在"，保证不了"段号对"。
   所以：数据类断言 + 人工抽查，缺一不可；能钉死的就写进人工覆盖表。
