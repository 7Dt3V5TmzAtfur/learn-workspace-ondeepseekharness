# 重构前的六项缺口：三视角分析与方案选择

> 结论先行：6 项缺口里，2 项是**数据结构错了**（改渲染没用，必须改数据），
> 2 项是**流程缺环节**（QA、来源标注），2 项是**界面没接上**（archify HTML、语音）。
> 下面每项都给三个视角，最后选一个并说明为什么放弃另外两个。

---

## 缺口 1：三色高亮加在整段上，而不是原文关键短语上

### 现状

`renderAnnotatedHtml` 把整段套一个颜色 class：

```js
const cls = a ? TIER_CLASS[a.tier] : ''
return `<section class="sc-seg ${cls}" data-id="...">${tag}${body}</section>`
```

标注数据也只有 `segmentId`，没有"原文中哪几个字"。

### 视角一：用户的注意力机制

用户要的是「**用三种颜色加粗原文**」，目的是在通读时眼睛自动跳到关键短语。
整段变色 → 一整块色块，人眼无法区分"这段里哪个词最关键"，三色退化成一个标签，
注意力机制失效。**这是功能失效，不是美观问题。**

### 视角二：数据结构

要句内高亮，标注条目必须能定位到"段落里的第 N 到 M 个字"。
只存 `segmentId` 做不到。两种存法：

| 存法 | 优点 | 缺点 |
|---|---|---|
| 存字符偏移 `{start, end}` | 精确、渲染零成本 | 原文一旦重切段落就全错位 |
| 存**原文短语** `quote` + 渲染时查找 | 抗错位、人能读懂、可校验 | 有重复短语时要消歧 |

存短语更稳，且天然可校验（渲染时找不到 = 标注错了，能直接报错）。

### 视角三：规则约束

三色预算按**字数**算（core ≤10%、hard ≤8%）。整段高亮时，一个 200 字段落算 200 字，
预算瞬间用光——这就是之前"长段落无法进核心档"的真正原因。
改成短语级后，一句 20 字的高亮只花 20 字预算，**预算模型才真正可用**。

### 选定方案

**标注条目增加 `quote`（原文片段）+ 可选的 `start`/`end` 偏移**，渲染时：
1. 在段落里查找 `quote`，找到就 `<strong class="sc-hl-core">片段</strong>`
2. 找不到 → 校验报错（拒绝保存），提示模型"你引用的原文不存在"
3. 预算按 `quote` 字数算

**放弃**：整段变色（功能失效）；纯偏移（重切段落就崩）。

**三色语义**（沿用原设计，颜色承载不同认知负担）：
- 蓝 core：定义/结论 → 必须记住
- 红 hard：难点/易错 → 需要停下来想
- 绿 ref：例子/补充 → 扫一眼即可

## 缺口 2：没有 QA 问答对

### 现状

完全没有。`drills.jsonl` 只记费曼复述。

### 视角一：用户的明确要求

原始需求写了：「文件后添加QA提问和回答，辅助自己回忆刚才看了什么。（每个QA不超过100字）」
用户读了 182 段后，需要**按文件**给自己留一份可速查的自测清单。

### 视角二：学习科学

对应「主动回忆」（retrieval practice）：读完后立刻自测，比再读一遍有效得多。
但 QA 必须是**问题指向原文要点**，不能是"这段讲了什么"这种空问题。

### 视角三：工程落点

QA 应该挂在**文件**（docId）上而不是段落上——用户要的是"读完这份资料，我能回忆起什么"。
存储用 `qa.jsonl`，每条形如 `{q, a, segmentIds[]}`，与 `terms.jsonl` 同构。

### 选定方案

新增工具 `study_qa`（或并入 `study_save` 的 `kind: 'qa'`），
每条强制 `≤100` 字（问题+回答分别限制），并记录来源段落 `¶N` 以便回跳。
界面在「精读加工」页签底部展示，可折叠自查（答案默认隐藏，点击才显示——
**这是主动回忆的关键，答案不能直接可见**）。

**放弃**：把 QA 混进思考题（思考题是费曼追问，量少而深；QA 是速查，量多而浅，两者混在一起会互相稀释）。

## 缺口 3：参考资料没标来源类型

### 现状

`references` 只有 `{title, kind, note}`，看不出「这段是我自己知道的」还是「原文里的」还是「我联网查的」。

### 视角一：用户的明确要求

原始需求：「你搜索网络也好，你用到的哪些资源？要呈列表的形式」，
并且明确要求区分 `原文` / `我的知识` / `联网检索`。

### 视角二：可信度分级

这三种来源的可信度和可追溯性完全不同：
- `原文`：最高，就在你手上，可核对
- `联网检索`：中等，有链接可回查
- `我的知识`：最低，模型记忆可能过期或有误

不标来源，用户无法判断该不该信。

### 视角三：实现成本

只需在 `references` 的每条上加 `source` 枚举 + `url`（联网检索时必填）。
校验规则：`source === '联网检索'` 时必须有 `url`，否则拒绝——
**强制"说联网了就得给出链接"**，防止编造。

### 选定方案

`references[]` 增加 `source: '原文' | '我的知识' | '联网检索'` 和可选 `url`。
界面按来源分组/加色标，联网条目渲染成可点链接。

## 缺口 4：archify 生成了 HTML，但界面看不到

### 现状

我写了 `archify-graph.js` 能把 relations 转成 archify 候选，也能跑通 `finalize`
（validate/deliver/check 三道门都过了），但**没有接进 `StudyService` 和界面**。
界面现在显示的是我自己写的 SVG。

### 视角一：用户要的是"技能来做"

原始需求原话：「这部分可以用这个一个技能来实现（archify）」。
用户要的是**用 archify 这个既有能力**，不是让我重写一个 layout 引擎。

### 视角二：维护成本

自己写 SVG = 永远在修布局 bug（这次就修了 0 穿节点、标签溢出、绕路）。
archify 有 schema 校验 + 三道质量门，布局问题由它负责，我只管"数据怎么映射"。

### 视角三：集成方式

两种：
- **构建期**：保存关系图时调 archify 生成静态 HTML，存进 `.study/<docId>/graph.html`，
  界面用 `<iframe src="/asset/.../graph.html">` 展示。
  优点：一次生成多次查看，快；缺点：改了关系要重新生成。
- **运行期**：每次请求现算。缺点：archify 是 CLI，跑一次几百 ms 到几秒，太慢。

### 选定方案

**构建期生成 + 资源路由托管**：
1. `saveRelations` 成功后，同步生成 `graph.html`（archify CLI，失败不阻塞保存，只记警告）
2. 界面 iframe 加载 `/study-copilot/api/asset/<docId>/graph.html`
3. 保留 Mermaid 源作为兜底（archify 失败时降级）
4. 提供手动「重新生成」按钮

**关键约束**：archify 大图会因 `projected-text-readability` 失败。
解决：**关系图节点超过 18 个时，按部分拆成多张图**，每张一个 tab。
（18 是实测出来的：2200px 画布 + 12.5px 字，缩到 1440 视口仍可读的上限）

## 缺口 5：没有语音提问

### 现状

界面只有文本框。

### 视角一：用户场景

原始需求：「阅读过程中你要我如果有不懂的我会提问你这用语音来提问」。
读书时手在翻页/做笔记，打字打断节奏，语音是刚需。

### 视角二：技术路径

| 方案 | 可行性 |
|---|---|
| 浏览器 `SpeechRecognition`（Chrome/Edge 自带） | 零依赖，但要走谷歌服务器，国内可能不可用 |
| 自己接 ASR | 要装模型，重 |
| 复用 Harness 已有语音输入 | 最轻，但要确认它存在 |

### 视角三：降级设计

不能因为语音不可用就让提问功能失效。必须：**语音是增强，文本框是主体**。
检测到 `SpeechRecognition` 就显示麦克风按钮，不支持就隐藏。

### 选定方案

优先复用 Harness 自带语音输入（若可用）；否则加 `SpeechRecognition` 按钮，
不支持则隐藏按钮并提示"可用键盘输入"。**无论如何文本框始终可用。**

## 缺口 6：渲染层与数据层耦合（隐藏问题）

### 现状

`renderAnnotatedHtml`、`renderPreflightHtml` 都在 service 里自己拼字符串，
导致"排版错乱"这类问题反复出现（已经修过一轮嵌套 `<p>`）。

### 视角一：职责

渲染是**纯函数**：数据 → HTML。不该和存储、工具调用混在一个类里。

### 视角二：可测性

现在排版 bug 只能靠跑接口发现。抽成纯函数后可以直接单元测试"给定数据，输出什么 HTML"。

### 视角三：复用

AI 生成的 Markdown、用户手写的 Markdown、原文，都要走同一套渲染。
现在分散在多处，规则会漂移。

### 选定方案

抽出 `lib/render.js`：所有"数据 → HTML"集中在这里，`service` 只负责取数据、
调 render、返回。测试直接打 render。

## 组织元素重排：为什么现在的划分不好

### 现状问题

现在 6 个技能 + 1 个插件，但**技能之间的边界是按"流程阶段"切的，不是按"能力"切的**，
导致：
- `study-annotate` 既要管标签又要管三色，职责过重
- `study-map` 产出的 Mermaid 还要再转 archify，多一道手工
- 没有技能负责"读完留 QA"这件事

### 三个视角

**视角一：认知负荷**
每个技能应当对应"用户此刻在做的一件事"。用户读一段 → 标注；读完全文 → 留 QA/自测。
README 里说"一个技能一件事"，现在明显违反。

**视角二：可组合性**
按能力切（提取/建档/标注/追问/图谱/考核）比按阶段切更容易复用——
比如"追问"在阅读中和考核中都要用。

**视角三：Agent 调用成本**
技能越多，Agent 越容易选错。6 个是合理上限，但每个的 `description` 必须能一句话区分。

### 重排方案

保留 6 个技能，但**重新定义职责边界**：

| 技能 | 一句话职责 | 变化 |
|---|---|---|
| `study-companion` | 总控：判断当前该做哪一步 | 状态机更明确 |
| `study-preflight` | 读前六段式（含 archify 图的触发） | 增加"每部分对应关系图" |
| `study-annotate` | 逐段七类标签 + **原文短语三色高亮** | 核心改动 |
| `study-recall` | **读完留 QA + 最小 MVP 行动** | **新增**（原属 annotate 尾步） |
| `study-explore` | 术语/概念追问（带段落上下文） | 原 explain-term，扩到概念 |
| `study-map` | 知识点关系图 → **调 archify 出 HTML** | 改动 |
| `study-feynman` | 读后考核 | 保持不变 |

## 执行顺序（依赖决定）

1. **数据结构先行**：`quote` 字段、`source` 字段、`qa.jsonl` —— 这是地基
2. **渲染抽离**：`lib/render.js` —— 让后面所有改动可测
3. **archify 集成**：service + 资源路由 + 界面 iframe
4. **大图拆分**：按部分拆，解决可读性
5. **语音 + QA 界面**
6. **审计脚本升级**：把上面每条都变成断言

## 用什么方式验证

现有 79 项测试 + 44 项审计**都没能发现这些缺口**，说明测试维度不够。
新增三类断言：

1. **数据契约**：标注必须带 `quote`，且 `quote` 必须在原文中出现
2. **渲染结果**：`annotatedHtml` 里 `<strong class="sc-hl-*">` 的数量 == 标注条数；
   且高亮片段必须是原文子串
3. **成品可用性**：archify HTML 存在、能通过 HTTP 取到、体积合理（>10KB 说明真有内容）
