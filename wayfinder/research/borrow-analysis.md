# 借鉴分析：learn-from-materials → 学习工作台

用户判断：**界面设计不学它（我们自己的更好），只学内容组织、结构、导航、流程、视觉逻辑。**
要求：逻辑清晰、足够明确、**不要太复杂**。

下面每个维度至少三个角度，最后给出"抄什么 / 不抄什么"的结论。

---

## 维度一：内容组织 —— 「单元」这一层是骨架

### 角度 1.1：它的组织链条是四层，我的是两层

它：`原文文件 → 来源块 sourceBlock → 单元 unit → 知识卡片（framework/claim/rule）`
我：`原文 → 段落 ¶N`，然后直接跳到 `标注 / 图谱节点 / QA`。

**缺的是"单元"这一层。** 后果是我现在的系统里：

- 182 个段落是平铺的，用户看不到"这一章分几块、每块讲什么"
- preflight 的 4 个 `parts` 是模型自己编的切法，跟原文 20 个真实小节**没有 ID 关联**
- 图谱 33 个节点和 182 段之间没有映射：图上点一个节点，不知道该跳哪一段

这三个断裂都指向同一个原因：**没有一个把"原文小节"和"知识块"绑起来的中间层。**

### 角度 1.2：单元内部有固定的十个格子

它的每单元结构是固定的：
`Core Idea / Frameworks / Key Concepts / Mental Models / Anti-patterns / Worked Example / Takeaways / Expandable Conclusions / Connects To / Source Range`

这个设计的价值不在格子多，而在**每个格子回答一个固定问题**：

| 格子 | 回答的问题 | 用户的实际困惑 |
|---|---|---|
| Core Idea | 这块一句话是什么 | 读完不知道重点 |
| Key Concepts | 里面有哪些概念 | 概念散落 |
| Anti-patterns | 什么做法是错的 | 只会套用不会判断 |
| Worked Example | 怎么用 | 不会迁移 |
| Takeaways | 记住哪三条 | 记了一堆没重点 |
| Connects To | 和哪块有关系 | 知识点孤立 |
| Source Range | 对应原文哪几段 | **无法回到原文核对** |

最后一条是关键：`Source Range` 让每个单元**可回查**。

### 角度 1.3：它取消了"数量完成线"

原文明确写：framework、glossary、decisionRule、conclusion **都不设下限，不设"达到即可结束"的完成线**；同时禁止为凑数编造。

对照我的系统：我给标注设了 **10%-20% 高亮预算**，给 QA 设了 **6-12 条**。这些数字本意是好的（防止标太多失去重点），但副作用是：**模型会为了达标而凑**。我这次补标 145 段时就是这种感觉——为了把覆盖率从 1.6% 提到 11%，我机械地给每段找一句话，产出了一批"按需""部署应用"这样的碎片。

### 角度 1.4（反面）：它的文书层数不能抄

同一个"关系是否成立"它要在 4 个地方各写一遍（unit-records 的 relationCandidates、relation-ledger 的 candidates+decisions、action-rule-ledger 的 relationReview、content-review 的 structureReviews）。示例只有 3 页材料就产出 11 个候选、4 个 scope、两份 structure-review。

**用户明确说"不要太复杂"**，所以这一层坚决不抄。

### 维度一结论

| 抄 | 不抄 |
|---|---|
| **引入"单元"作为组织骨架**，向上接原文小节，向下接知识点 | 十个格子的完整清单（太多，砍到 5 个） |
| 单元必须带 **来源段范围**（`segmentIds`），保证可回查 | 每单元一份 `unit-records.json` + 一份 `.md`（双份维护） |
| **取消标注数量的硬性下界**，改成"每单元必须有核心结论" | 完全取消预算（高亮太多确实会失去注意力，上界要留） |

## 维度二：结构 —— 双向映射而非单向清单

### 角度 2.1："读完"不等于"提炼到"

它最锋利的一条：正向审计（我读了哪些）会被"我读了"糊弄；只有**从原文块反查**才能抓到"整段没进知识库"。

对照我的系统：我的 `coverage()` 是正向的——数了哪些段有标注。这次补标后 182/182 全有标注，**看起来完美**。

但实际质量如何？抽查一下就知道：`¶136`（表4-2 对比表）的标注是 `#c 表格 | 维度`，quote 是「维度」两个字。**这一段等于没提炼。**

正向审计说"100% 覆盖"，反向一看是"有标注但没内容"。这就是正向审计的盲区。

### 角度 2.2：双向映射的具体形状

它的 `summary-ledger` 形状是：

```
claim (原文里的一句话)  ←→  summaryRef (产出里的一个位置)
正向：每条 claim 至少映射一个 summaryRef
反向：每个 takeaway/conclusion 必须被至少一条 claim 支撑
两侧任一侧断裂 → 阻止交付
```

搬到我的系统，对应的就是：

```
单元 taskeaway  ←→  段落 ¶N 里的 quote
正向：每个单元的 takeaway 必须能在原文找到依据段
反向：每个"核心档"段落必须被至少一个单元引用
```

反查能抓到两类错：
- **孤儿 takeaway**：单元里写了结论，原文里没依据 → 编造
- **孤儿核心段**：原文里标了核心，但没有单元收纳它 → 漏提炼

### 角度 2.3：关系必须逐类表态，不是逐条

我的 `validateRelations` 已经要求八类关系逐类表态（这是对的，已实现）。但它还缺一环：**边必须落回具体段落**。

现在 40 条边里 25 条有 quote，15 条标推断。我上一轮刚修了 13 条"quote 不是原文"的假边——那批边读起来完全通顺，是拼接出来的。**没有 `segmentId` 的边，人眼根本查不出来。**

### 维度二结论

| 抄 | 不抄 |
|---|---|
| **单元 takeaway ↔ 原文段落 双向映射**，两侧都断言 | 四层账本（coverage-audit + reverse-coverage + summary-ledger + content-review） |
| **每条知识图谱边必须有 `segmentId`**（不只是 quote） | `relation-ledger` 的 candidates/decisions 双层结构 |
| **反向覆盖检查**：哪些段有标注但 quote 太短/无意义 | `content-review.json` 的二次复核 |

## 维度三：流程与导航 —— 一条主线，不是五个并列页签

### 角度 3.1：它只有一个入口 `INDEX.md`

它的全部产出挂在 `INDEX.md` 下：units / methodology / glossary / coverage。用户从一个入口走下去。

我的界面是**五个并列页签**：读前建构 / 读中加工 / 知识图谱 / 读完自测 / 费曼考核。

问题在于：**并列 = 没有主线**。用户打开不知道"我现在该点哪个"。

### 角度 3.2：它的深度模式只问一次

`learning-depth-modes`：提取前只问一次"快速了解 / 系统学习"，之后全部流程按这个档位走。升级时沿用同一个 `pageId`。

我的系统没有这个分叉，一律走"全量标注 + 全量 QA"。对一份 182 段的资料，这是对的；但如果用户只想快速看一眼，这套流程太重。

### 角度 3.3：导航的核心是"我在哪 + 还有多少"

它靠 `INDEX.md` + `coverage-audit` 回答这两个问题。

我的界面：不知道当前位置（滚动条位置 ≠ 结构位置），不知道还剩多少（覆盖率藏在自测页的一个数字里）。

**用户说"导航不清晰"，本质是这两条没答上。**

### 维度三结论

| 抄 | 不抄 |
|---|---|
| **单元作为导航单位**：左侧列出所有单元，当前单元高亮，未完成单元标灰 | 单一 `INDEX.md` 静态文件（我们是交互界面，不需要） |
| **进度按单元算**，不按段落算（"3/20 单元完成"比"37/182 段"有意义得多） | 两档深度模式（用户没说需要，加了反而多一个选择负担） |
| 保留五页签，但**由单元驱动**：每个单元内有自己的读前→读中→自测 | 十层审计文书 |

## 综合：这次要改什么（三条，不多）

用户说"不要太复杂"。所以只做三件事，每件都直接对应一个已被确认的缺陷：

### ① 引入「单元」层（解决"结构不清晰"）
- 新建 `units.json`：每个单元 = 原文小节（真实标题）+ 段范围 + 一句话核心 + 若干知识点 + 对应的图谱节点
- preflight 的 `parts` 不再单独存在，改为**引用单元**（`part.unitIds`）
- 图谱节点必须挂 `unitId`

### ② 单元级双向映射（解决"内容散"）
- 每个单元必须有 `takeaways[]`，每条 takeaway 必须带 `segmentId`
- 反向：每个 `core` 档段落必须至少被一个单元收进去
- 任一侧断裂 → 校验失败并指出具体哪条

### ③ 导航按单元（解决"不知道自己在哪"）
- 界面左侧单元列表 + 当前位置 + 单元级进度
- 这属于界面，本轮先只做数据层（用户选了 C），但数据结构要为它留好位置

---

## 明确不抄的（写进 Out of scope）

- 十层审计文书（coverage-audit / reverse-coverage / summary-ledger / content-review / action-rule-ledger / relation-ledger / source-manifest / source-map / material-security / performance-report）
- 两档深度模式
- 单元内部的十个格子（砍到 5 个：核心 / 知识点 / 难点 / 例子 / 记住什么）
- 它的界面与视觉设计（用户明确说我们的更好）
- `unit-dependency-map` 增量更新表（单用户本地工具，没有增量场景）
